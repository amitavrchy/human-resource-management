# Deployment and operations

## Compose lifecycle

```sh
node scripts/init-env.mjs
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps
```

PostgreSQL becomes healthy, the one-shot migration service applies committed migrations, then API readiness allows the web service to start. A failed migration prevents API startup. AI starts independently; its health endpoint reports whether the provider is configured. The API has separate `/health/live` and `/health/ready` probes. Probe failures do not expose database credentials.

The application images run as unprivileged users. Uploads are owned by the API user; the AI process owns its vector-storage directory. API/AI have no host port bindings. Health checks and graceful process handling are included. `docker compose down` stops the stack while preserving named volumes. Do not remove volumes to perform a normal upgrade.

Set `WEB_PORT` and `CLIENT_ORIGIN` together when changing the local port. `WEB_BIND_ADDRESS` defaults to `127.0.0.1`. `POSTGRES_DB` defaults to `peopleos`. Database passwords generated by the initializer are hex strings, so they can safely appear in the database connection URL. If supplying your own password, URL-encode it in custom connection URLs.

For hosting, terminate TLS at a trusted ingress on this host, set `CLIENT_ORIGIN=https://your-domain.example` and proxy to the loopback web port. If using a different host/network, review its firewall and forwarding headers before changing the binding. The build-time web API target defaults to `http://api:4000` inside Compose. Never expose PostgreSQL, raw uploads, the AI service or Chroma directly.

## Upgrade

1. Back up PostgreSQL and uploads; retain the current image/source revision.
2. Pull the intended Git commit and review migrations and environment changes.
3. Run `docker compose up --build -d --wait`. Inspect `docker compose logs migrate` and service health.
4. Verify sign-in, a scoped directory fetch and a private download. Run the loopback smoke script only against an isolated QA deployment; it creates a test workspace.

Committed migrations are additive. Application rollback and database rollback are separate operations: restore a tested backup into a fresh database if a migration cannot be safely reversed. Do not point a restore command at a live employee database without a reviewed restoration plan.

## Backups

Maintain encrypted, access-controlled backups of all three named volumes. PostgreSQL and uploads should represent the same recovery point. Handbook vectors can be rebuilt from saved source text and a configured provider key, but retaining them avoids re-embedding costs.

Create the database dump inside the container, then copy it out; this avoids corrupting a binary dump through older PowerShell output redirection:

```sh
docker compose exec postgres sh -c 'pg_dump -U peopleos -d "$POSTGRES_DB" -Fc -f /tmp/peopleos.dump'
docker compose cp postgres:/tmp/peopleos.dump ./backups/peopleos.dump
```

Create/protect the `backups` directory first. Snapshot `uploaded_files` and `handbook_vectors` using your volume/host backup system. Periodically restore PostgreSQL into a separate test database and verify private downloads against the corresponding file snapshot. Volume names are prefixed by the Compose project name, so confirm the actual names using `docker volume ls`.

## Demo seed

The `seed` profile waits for a healthy API so the upload volume has the correct owner. Set `DEMO_PASSWORD` explicitly, then run `docker compose --profile demo run --rm seed`. Do not seed production employee deployments. The seed preserves edited data and existing passwords on repeat runs; use a separate demo database when a fresh demo is needed.

## Configuration reference

| Setting                      | Where                        | Purpose                                                                         |
| ---------------------------- | ---------------------------- | ------------------------------------------------------------------------------- |
| `DATABASE_URL`               | Native API / Compose-derived | PostgreSQL connection; required at runtime                                      |
| `JWT_SECRET`                 | API                          | Random signing secret, at least 32 characters; placeholders rejected            |
| `AI_SERVICE_TOKEN`           | API and AI                   | Same random token, at least 32 characters; never sent to the browser            |
| `CLIENT_ORIGIN`              | API                          | Exact allowed browser origins; comma-separated for native QA                    |
| `API_INTERNAL_URL`           | Web build                    | Same-origin API proxy destination; rebuild web when changing it                 |
| `OPENAI_API_KEY`             | AI only                      | Enables model and embedding calls                                               |
| `OPENAI_MODEL`               | AI                           | Configurable model; defaults to `gpt-4.1-mini`                                  |
| `OPENAI_EMBEDDING_MODEL`     | AI                           | Defaults to `text-embedding-3-small`; re-index if changing embedding dimensions |
| `UPLOAD_DIR` / `CHROMA_PATH` | API / AI                     | Persistent storage locations                                                    |
| `TRUST_PROXY`                | API                          | Trusted proxy hop count; default 0 natively, 1 in Compose                       |
| `DEMO_PASSWORD`              | Explicit seed only           | Initial demo accounts; never automatically seeded                               |

Changing the JWT secret invalidates access tokens. Revoke refresh-session records as part of a compromised-secret incident so old refresh tokens cannot establish new sessions. Rotate the AI service token in both services together.

## Logs and scaling

`docker compose logs --tail 100 api web ai migrate` provides service diagnostics. Avoid sharing logs containing credentials or real employee data. External observability is not pre-connected; configure the approved monitoring provider and alerts for failed readiness, repeated errors, storage capacity and provider outages in your hosting environment.

The supplied file/vector volumes and rate limiter target a single API instance and one AI process. Multiple replicas need shared durable upload storage, a reviewed vector architecture and distributed/edge throttling. Do not simply launch multiple workers against an unreviewed shared Chroma directory.
